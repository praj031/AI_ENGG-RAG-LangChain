Frequently Asked Questions
1. RAG fundamentals
1. What is the difference between an LLM and RAG?
LLM is the model that generates the answer. RAG is a system around the LLM that retrieves relevant external information and puts it into the prompt/context before generation.

2. Why do we need embeddings at all?
Because the database cannot meaningfully perform semantic similarity on raw text. Embeddings convert text into vectors so we can find content that is semantically similar, not just textually identical.

3. Do we need two models for RAG?
Usually yes: an embedding model for retrieval and a generative LLM for producing the final answer. They can be from completely different providers.

4. Does RAG train the LLM on our documents?
No. Normally RAG does not modify model weights. The document is retrieved at inference time and supplied as context to the LLM.

5. If we give the LLM a document, how does it know to answer from that document?
The application retrieves relevant content and places it in the model's context, usually with instructions such as "answer using this context." It is not learning the document permanently.

6. How does the LLM decide whether to retrieve or answer directly?
It depends on the RAG architecture. You can always retrieve, or use a router/agent/classifier to decide whether retrieval is necessary. The LLM itself doesn't magically control Qdrant unless you explicitly give it that capability.

2. Embeddings and vectors
7. What exactly is an embedding?
An embedding is a numerical vector representing some semantic properties of the input. Similar meanings tend to produce vectors that are close according to an appropriate similarity metric.

8. Why are embeddings different dimensions? Who decides the dimension?
The embedding model architecture determines the output dimension. For example, one model may produce 768 dimensions and another 1536; you don't choose an arbitrary dimension when using the model.

9. Can I store a 1536-dimensional vector in a collection configured for 768 dimensions?
No. The vector dimension must match the collection/index configuration. Changing the embedding model to one with a different dimension generally means creating/reconfiguring the collection and re-embedding the data.

10. What happens if I ingest with one dimension and query with another?
The search cannot work correctly because the vectors exist in different vector spaces. In practice, the vector database will generally reject a dimension mismatch rather than perform a meaningful comparison.

11. Is vector dimension the same thing as model parameters?
No. Parameters are the learned weights inside a model, often billions of values. Embedding dimension is the number of values in one output embedding vector. They are completely different concepts.

12. Why not simply use a dictionary containing all words instead of embeddings?
A dictionary gives you discrete/token-level representation, but it doesn't naturally capture semantic relationships. Embeddings allow concepts such as car and automobile to be represented as nearby points even when the words differ.

13. Why do we need an embedding model? Couldn't traditional algorithms do this?
Traditional methods such as TF-IDF or BM25 are useful for lexical matching, but learned embeddings capture semantic relationships much better. In production RAG, dense retrieval and lexical retrieval are often combined.

14. Can embeddings generated by one provider be used with another provider's LLM?
Yes. The embedding model and generation model are independent. The important requirement is that the query and document embeddings use the same compatible embedding model/space.

3. Similarity and distance
15. How do I decide between cosine, dot product and Euclidean distance?
It depends on the embedding model and how its vectors are intended to be compared. Cosine focuses on direction, dot product considers direction and magnitude, and L2 measures geometric distance. Usually follow the embedding model's recommended metric.

16. Why isn't magnitude important for text embeddings?
With cosine similarity, magnitude is explicitly normalized away, so only the angle/direction matters. This is useful when semantic orientation matters more than vector length.

17. What is a unit vector?
A vector whose magnitude is exactly 1. Normalizing vectors to unit length makes cosine similarity equivalent to their dot product.

18. Why would we choose Euclidean over Manhattan distance?
They represent different geometric assumptions. L2 measures straight-line distance; Manhattan measures movement along individual dimensions. For modern text embeddings, cosine/dot product are generally more common than Manhattan, so don't choose based only on "outliers."

4. Vector DB / Qdrant
19. Does Qdrant search every vector for every query?
With exact/flat search, essentially yes. With ANN indexes such as HNSW, it intelligently navigates an index instead of comparing against every vector.

20. What is the difference between exact search and ANN?
Exact search checks all candidates and gives the true nearest neighbors, but becomes expensive at scale. ANN sacrifices a little recall to dramatically reduce search cost and latency.

21. What is HNSW actually doing?
HNSW builds a graph of vectors with multiple levels. Search starts at a sparse upper level and progressively moves toward more relevant regions, eventually searching a denser lower level.

22. Who creates the HNSW layers?
The HNSW algorithm creates them during index construction according to its probabilistic layer-assignment mechanism. You don't manually decide which vector belongs to which layer.

23. What does HNSW tuning actually mean?
Mainly controlling the trade-off between search quality, latency, memory and indexing cost. For example, increasing search effort generally improves recall but costs more CPU/time.

24. Is HNSW specific to Qdrant?
No. HNSW is an ANN algorithm, not a Qdrant feature. Qdrant uses it, but other vector databases/search engines can also implement HNSW.

25. If I change the vector database, does the search algorithm change?
Potentially. Different databases support different indexes and implementations. The important distinction is vector database ≠ search algorithm; HNSW, IVF, Flat, etc. are indexing/search techniques that databases may implement.

26. Which vector DB is used most in production?
There isn't one universal winner. Common choices include Qdrant, Pinecone, Weaviate, Milvus, pgvector, OpenSearch, etc. The right choice depends on scale, existing infrastructure, filtering, operational requirements and managed-vs-self-hosted preference.

27. Can we use OpenSearch instead of Qdrant?
Yes. OpenSearch supports vector/semantic search and can be attractive when you're already invested in the AWS/OpenSearch ecosystem. Qdrant is simply the dedicated vector database we're using for this course.

28. Does a vector database have joins like PostgreSQL?
Not in the same relational-database sense. Vector DBs are optimized around vector retrieval plus metadata/filtering; if you need complex relational joins, PostgreSQL/pgvector can be a better fit.

5. Chunking and retrieval
29. What happens if related information gets split across different chunks?
That's a real RAG problem. One chunk may contain the question's relevant information while another contains the missing context. Solutions include better chunking, overlap, parent/child retrieval, metadata, contextual retrieval or retrieving multiple related chunks.

30. Is indexing performed when the user asks a question?
Normally no. Indexing is an ingestion-time process: parse → chunk → embed → store/index. At query time you embed the query and perform retrieval against the existing index.

31. Why do we embed the query too?
Because the query needs to enter the same vector space as the document chunks. You compare embedding(query) against embedding(chunk) to find semantically similar chunks.

32. How do we decide how many chunks to retrieve?
It's a retrieval-quality/context-budget trade-off. Too few can miss evidence; too many introduce irrelevant information and increase latency/token cost. Usually you tune top-K experimentally.

33. What if the most relevant information isn't in the top-K?
That's a retrieval failure. You can improve chunking, embedding models, query transformation, K, ANN configuration, filtering, hybrid search or add a reranking stage.

6. Production RAG questions
34. What happens if Qdrant goes down but PostgreSQL is still available?
Your application should treat the vector store as a separate dependency and have a failure strategy: retry/timeouts, fallback behavior, degraded functionality, monitoring and possibly rebuilding the vector index from the source data in PostgreSQL/object storage.

35. How do we securely give an LLM data from our database without giving it database access?
Don't give the LLM raw DB credentials. Put a controlled service/tool layer between them that performs authorized queries, validates inputs, limits returned data and enforces permissions.

36. How does a chatbot maintain conversation context?
The LLM API itself generally doesn't "remember" previous calls. Your application maintains conversation history/state and sends the relevant history with subsequent requests, often combined with summarization or memory retrieval.

37. Can RAG be combined with agents?
Yes. Traditional RAG usually follows a relatively fixed retrieve → generate flow. Agentic RAG lets an agent decide when/how to retrieve, potentially use multiple retrieval tools, reformulate queries and perform several retrieval steps.

7. OpenRouter / LLM API
38. What is OpenRouter?
OpenRouter is an API gateway/aggregator that gives you access to models from multiple providers through a common interface. It's useful for experimenting with different models without integrating every provider separately.

39. Is OpenRouter similar to Amazon Bedrock?
Conceptually yes in the sense that both can provide access to multiple models through an API layer, but their provider ecosystems, infrastructure, billing, enterprise features and AWS integration are different.

40. Why do multiple providers offer the same model on OpenRouter?
The underlying model may be the same while different providers host/serve it. They can differ in infrastructure, latency, pricing, availability and sometimes capabilities/configuration.

41. Can we use a local LLM instead?
Yes. If your local model exposes a compatible API, you can point your application/SDK at it instead of a hosted provider. The main trade-offs are hardware, latency, model quality and operational complexity.

42. What is streaming vs non-streaming?
Non-streaming: wait for the complete model response and then return it.
Streaming: receive tokens/chunks progressively, which improves perceived latency for chat applications.

43. How should API keys be handled?
Never hardcode or commit them. Use environment variables locally and a proper secret manager/secret store in production.
